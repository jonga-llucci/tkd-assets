2. FILE STRUCTURE & RESPONSIBILITIES
------------------------------------------------------------

- Index.html    : Single frontend file. All views, CSS, JS, navigation.

3. SPREADSHEET SCHEMA (The Data Source)
------------------------------------------------------------
[Tab: Users]
- Col A: Username (String, email address, Primary Key)
- Col B: Password (String)
- Col C: BeltLevel (Integer, 1-14)
- Col D: LastActive (Date)
- Col E: Streak (Integer)
- Col F: DisplayName (String)
- Col G: isAdmin (String, "Y" = admin)
- Col H: FCMToken (String, populated by WebIntoApp bridge)
- Col I: RegisteredDate (Date, set on registration)
- Col J: SubscriptionDate (Date, set on payment — blank during trial)

[Tab: Questions]
- Col A: QuestionText
- Col E-H: Options (Randomized on load)
- Col L: CorrectAnswer (Matches one of E-H)
- Col O: qId (Unique String ID - CRITICAL for SRS)
- Col Q: Exam (Y/N - "N" = Flashcard Only)
- Col R: BeltLevel (Integer)
- col S: SimpleTerm (Text for Matching game)
- col T: SimplifiedDef (Text for True / False game)
- col U: GameCategory (answer categorisation for future game features)
- col V: TimeLimit (Difficulty based time limit for future game features)
- col W: TulName (Tul question is related to for future game features)

[Tab: UserProgress] (SRS Data)
- Col A: Username
- Col B: qId
- Col C: Score (Cumulative)
- Col D: Bucket (1-4, Spaced Repetition Stage)
- Col E: LastDate (Date)

[Tab: Tuls] (Trump Cards)
- Col A: Name
- Col B: Movements
- Col C: Stances
- Col D: ReadyStance
- Col E: Difficulty
- Col F: BeltLevel
- col G: Interpretation
- Col H: ImageURL
- Col I: KoreanReadyStance

[Tab: HighScores] (Auto-created on first Infinite Warrior game)
- Col A: Username
- Col B: InfiniteWarrior (Integer, all-time personal high score)

[Tab: Belts]
- Col A: Belt (String, display label e.g. "6th Kup - Green Belt")
- Col B: BeltLevel (Integer, corresponding numeric grade value)

5. NAVIGATIONAL & NON-FUNCTIONAL REQUIREMENTS
------------------------------------------------------------
- DRY Principle: One 'switchView(id)' function controls all UI transitions.
- Performance must be prioritised by accessing the minimum data required when needed. Do not pre-load data. Users will have frequent short sessions.
- At the bottom of the container / each screen there should be a navigation bar with icons for "Home" (returns to the home screen), "Account" (Goes to a screen which shows their grade which is selectale in a drop-down, and the ability to change their password) and, "About" (Contains information in section 8). If any of these are selected during game play a confirmation pop-up appears and if the user chooses to "Exit" rather than "Stay & Play" they will be shown their results including incorrect answers to review (unless they have ansered 0 questions).
- At the end of a game, in the results box show a percentage score as a whole number, a pass is =>75%
- View Naming: All HTML IDs must follow 'view-[name]' (e.g., view-login, view-results).
- Session Exit: If 'isQuizActive' is true, Home/Logout must trigger 'showExitWarning'.
- Session Review: Upon exit, user must receive grade/review for answered questions unless they have not answered any questions
- The review-list container must have sufficient vertical space (e.g., max-height with overflow-y: auto) to display all incorrect answers without cutting off content.
- Single-Source Data: All quiz and trump data must flow from the Spreadsheet via google.script.run.
- Code Integrity: Be explicit when providing code updates. State which lines of code are to be added or replaced by line number.
- Universal Nav: handleNavigation(targetId) is the sole gatekeeper.
- Intercept: If isQuizActive == true, triggers showUniversalOverlay('QUIT_SESSION').
- Menu items must only display the mode name and icon; do not include question count indicators (e.g., /10 or /50) on the selection buttons.
- Pop-up System: Uses a single #result-overlay for:
    * Exit Warnings (Stay/Exit)
    * Session Results (Grade/Review)
    * Game Over / Victory announcements
- Do not add citations in code - [cite: X]
- loadAccountView() is called by handleNavigation when target is view-account. It fetches belt options on demand via getBeltOptions() and populates the grade selector. It is never called at login.
- goHome() must call handleNavigation('view-modes'), not switchView directly, to preserve the single-gatekeeper principle.
- switchView() maintains a master views array: ['view-login', 'view-modes', 'view-game-center', 'view-trumps', 'view-quiz', 'view-results', 'view-account', 'view-about', 'view-admin']. Any new view must be added to both this array and the navMap in updateNavIcons().
- loadAccountView() and loadAdminView() are called by handleNavigation on demand. Neither is called at login.
- result-overlay uses display:none via .hidden class. The .result-overlay CSS must not include display:flex — this is applied via .result-overlay:not(.hidden) to prevent the overlay blocking clicks when hidden.
- Admin nav item (nav-admin) is hidden by default and revealed on login only if res.isAdmin is true.

6. LOGIC & ALGORITHMS
------------------------------------------------------------
- Navigational Logic:
  * Variable Name: targetView (JS) / id (HTML).
  * ID Convention: view-[name] (e.g., view-modes, view-quiz).
  * Gatekeeper: handleNavigation(targetView) checks isQuizActive. If true, triggers showUniversalWarning.
  * Execution: switchView(targetView) clears all .view-container classes and adds .active-view to the target.
- SRS Logic: 
  * Bucket 1: 0 days | Bucket 2: 2 days | Bucket 3: 4 days | Bucket 4: 5 days.
  * Filter: (Today >= NextReviewDate) AND (BeltLevel <= UserGrade).
  * SRS Sort: For practice mode, questions are sorted by bucket ascending (bucket 1 first), then by LastDate ascending (most overdue first) within each bucket. This sort runs after filtering and before the 10-question slice. The answer option order is independently randomised per question.
  * SRS Fallback: If the SRS filter returns zero questions (all due dates in the future), the filter is relaxed to all eligible questions for the user's grade to ensure practice is always available.
  * SRS Sort (Practice): Questions sorted by bucket ascending, then LastDate ascending (most overdue first) within each bucket. Answer options are independently randomised.
  * SRS Fallback: If SRS filter returns zero questions, filter relaxes to all eligible questions for the user's grade.
  * SRS Update: updateQuestionScore fires for all modes including Mock Exam and Infinite Warrior.
- Exam Logic:
  * Filter: (Column Q == "Y") AND (BeltLevel <= UserGrade).
  * Limit: 50 questions.
  - Exam Length by Grade:
    * Grade 1–6:  10 questions, 15 minutes
    * Grade 7–10: 20 questions, 30 minutes  
    * Grade 11+:  50 questions, 60 minutes
  - Exam Category Weighting (col U): 10% Basics, 10% Numbers, 10% Belts, 30% Korean, 30% Patterns, 10% fill from uncategorised or any pool.
  - Exam Question Weighting: Within each category pool, questions are sampled with probability proportional to their BeltLevel (col R) — higher level = higher weight.
  - Mock Exam subtitle on home screen updates dynamically on login to reflect the correct time and question count for the user's grade.

7. GAME-SPECIFIC LOGIC
------------------------------------------------------------
- Tul Trumps - Initialization : getTulTrumpsData(username) in Code.gs (not TulGame.gs).
- Tul Trumps - Game State     : Managed in Index.html (playerHand, cpuHand).
- Tul Trumps - Minimum Deck   : Requires 4+ Tuls for the user's grade. Fewer = error message.
- Tul Trumps - Grade Lock     : Disabled and visually greyed for grades 1–5. Shows locked padlock badge and pop-up message. Grade 6 shows unlocked padlock. Grade 7+ shows no badge.
- Tul Trumps - Pop-up         : "Unlock this game in real life — you can play Tul Trumps when you reach 6th Kup."

- Infinite Warrior - Questions : Fetched via getQuizData(username, 'practice') in batches of 10. Reloads automatically when batch is exhausted.
- Infinite Warrior - Scoring   : +1 per correct answer. One wrong answer ends the game.
- Infinite Warrior - Progress  : Top bar fills relative to personal best + 1 (the target). Turns gold when personal best is beaten.
- Infinite Warrior - High Score: Personal best stored in Tab: HighScores. Fetched fresh on each game start (globals reset to 0 first to prevent stale values).
- Infinite Warrior - All Time  : getAllTimeHighScore() returns max across all users.
- Infinite Warrior - End Screen: Shows score, personal best, all-time best, and the question that ended the run with the correct answer. New high score triggers confetti.
- Infinite Warrior - SRS       : updateQuestionScore fires for every answered question.
- Infinite Warrior - No timer  : Per-question countdown is not used.age is shown and the game does not launch.

- Matching Pairs   - Only Question rows where col P = Y and has values in col S should be used.
- Matching Pairs   - Pairs: Formed with col S and col L.
- Matching Pairs   - Filtering: Cards are filtered by User Grade (Tab: Questions, Col R).
- Matching Pairs   - SRS: Questions should be prioritised using SRS buckets.

- True / False     - Only Question rows where col P = Y and has values in col T should be used.
- True / False     - Pairs: Formed with col S and col L.
- True / False     - Filtering: Cards are filtered by User Grade (Tab: Questions, Col R).
- True / False     - SRS: Questions should be prioritised using SRS buckets.

- Daily practise   - 10 questions
- Daily practise   - Blank answer options should not be shown
- Daily practise   - Filtering: Cards are filtered by User Grade (Tab: Questions, Col R).
- Daily practise   - Filtering: Cards are filtered by whether to be used as exam questions Col Q =='Y' (Tab: Questions, Col Q).
- Daily practise   - SRS: Questions should be prioritised using SRS buckets.
- Daily practise   - Selection highlighting during daily practise should show green for answers correctly selected and red if incorrect.
- Daily practise - Difficulty: User selects Easy (15s), Medium (10s), or Hard (5s) before starting. Default is Medium. Selection persists for the session and is controlled by practiceDifficulty global. Overrides per-question timeLimit (col V) in practice mode.

- Mock exam        - Time limit (shown with MM:SS timer) 60 mins
- Mock exam        - 50 questions
- Mock exam        - Passing mark => 75%
- Mock exam        - Blank answer options should not be shown
- Mock exam        - Filtering: Cards are filtered by User Grade (Tab: Questions, Col R).
- Mock exam        - Filtering: Cards are filtered by whether to be used as exam questions Col Q =='Y' (Tab: Questions, Col Q).
- Mock exam        - SRS: Not used for exam. Questions should be a random selection.
- Mock exam        - SRS: Answers submitted from mock exam should contribute to question SRS bucket.
- Mock exam        - Selection highlighting during the Mock Exam must be neutral (TKD Blue) and must not indicate if the answer is correct or incorrect until the final review.

10. UX STANDARDS
------------------------------------------------------------
- Primary Color: TKD Blue (#0d6efd) / TKD Red (#dc3545).
- Standardized UI: All card-based games must use consistent shadows, radii, and 'TKD Blue' accents.
- Feedback: Incorrect answers must be listed in the 'review-list' on results screen.
- In games a progress bar should be shown along the top
- Bootstrap icons should be used to make the interface user friendly - Flame for streak, controller for game centre, lightening for daily practice, stopwatch for mock grading
- In "mock exam" a countdown timer set from 60 minutes should be shown in the format MM:SS
- Animation: 0.3s ease-in-out on all view transitions.
- Maintain loading messages. They must be specific to / make sense for Taekwon-do training (section 10)
- Zero-Footprint Personalization: User data (Grade, Streak) influences logic silently; never use "Because you are [X]..." phrasing in UI.
- Transition: All views use a 0.3s ease-out translateY animation.
- Interactions: Buttons must use :active scales (0.98) for haptic-like feedback.
- Suppression: overscroll-behavior-y: contain must be present on the body to prevent pull-to-refresh loops.
- On completing a game with a passing mark (=>75%), or just completing the matching pairs game, then the confetti celebration should be shown. Confetti must be triggered with a high zIndex (e.g., 10000) to ensure it appears in front of the results card.
- Typography: All headings must use Bootstrap's fw-bold class rather than inline font-weight declarations. Font sizes should use Bootstrap's native scale (h1–h6, display-1 etc) or rem units consistent with the existing scale (2rem for primary headings, 1rem for labels, 0.85rem for supporting text). Custom CSS font-weight declarations are only permitted where a Bootstrap class is not available (e.g. inside fixed-position overlays or SVG elements). Never mix inline style font declarations with Bootstrap utility classes on the same element.
- Grade-locked content: Unavailable features are greyed (opacity 0.5) with a lock badge (bi-lock-fill, #adb5bd). Tapping shows a pop-up explanation via the standard result-overlay.Newly unlocked content shows bi-unlock-fill in green at grade 6, no badge above grade 6.
- Per-question countdown: Shown as an SVG ring in practice mode only. Fades out (opacity:0) rather than hiding (display:none) to prevent layout shift. Default 5 seconds, overridden by Questions col V (TimeLimit).
- Admin loading uses toggleLoad() consistently with all other views.

15. SUBSCRIPTION & PAYMENT
------------------------------------------------------------
- Platform: Stripe (stripe.com)
- Trial: 7 days from RegisteredDate (Col I). accessStatus = 'trial' during trial.
- Subscription: 30 days from SubscriptionDate (Col J). accessStatus = 'subscribed'.
- Expiry: accessStatus = 'trial_expired' or 'subscription_expired' after respective periods.
- Manually created users (no RegisteredDate): always accessStatus = 'active', never gated.
- Webhook: Stripe fires checkout.session.completed and invoice.payment_succeeded to GAS doPost() /exec endpoint. updateSubscriptionDate() writes now() to Col J.
- Signature verification: STRIPE_WEBHOOK_SECRET constant in Code.gs. Roll secret in Stripe dashboard and update constant + redeploy when compromised.
- Pricing Table: Stripe-hosted, embedded in view-subscribe via <stripe-pricing-table> web component. customer-email pre-filled via showSubscribePage(email).
- Customer Portal: Stripe-hosted. Linked from view-account "Manage My Subscription" button.
- Frontend gate: handleLogin() checks accessStatus. Expired users see overlay with View Plans button → showSubscribePage(). Active/trial/subscribed users proceed normally.
- Banner: #subscription-banner shown below Mock Grading on view-modes for trial and subscribed users. Trial shows orange warning. Subscribed shows green confirmation without subscribe button.
- Live vs Test: Update pricing-table-id, publishable-key, STRIPE_WEBHOOK_SECRET, and customer portal URL when switching from test to live. Never commit live keys to GitHub Pages — they are only in GAS Code.gs and Index.html (served by GAS, not public).
